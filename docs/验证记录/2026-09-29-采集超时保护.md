# 采集超时与暂停保护

2026-09-29，P1-4d 实现验证。

## 已实现

- 列表、券规则、门店共用请求生命周期保护：25 秒覆盖响应头及正文读取，独立定时器到期主动取消请求并返回 REQUEST_TIMEOUT。
- 超时进入全局暂停，不自动重试；保留任务游标。普通网络失败仍最多重试两次。
- 如果底层传输未响应取消，继续隔离该请求通道；即使操作恢复，也不发起第二个请求。迟到的结果不提交为成功数据；实际结束后额外等待 2 秒才允许后续请求。
- 暂停接口立即返回 worker_active / request_pending，状态接口同步提供；页面区分暂停完成与当前请求尚未结束。暂停不是取消已经发出的请求。
- 停服收到信号即停止调度采集，不再等 HTTP 连接结束才通知 worker。
- 不改动采集频率，不增加外部请求并发，不读取或输出登录凭据。

## 验证

完整 npm run check 通过，129 项测试通过。新增 5 项验证：无视取消的挂起请求、响应正文挂起与晚拒绝、正常成功/失败语义、超时全局暂停及原游标恢复、未结束请求期间暂停接口立即返回。

## 尚未证明

原长时间 in_flight 的根因尚未定位。本次部署前旧服务状态接口和暂停接口也出现超时，不能排除数据库或进程负载影响。独立定时器不能解决事件循环阻塞或数据库无限等待，不能据此宣称永久修复。旧进程退出后的历史 in_flight 记录不伪造为成功记录。自然运行稳定性仍待持续验收。

## 部署后真实结果

新版启动健康检查通过，已恢复过一次原任务。北京时间 11:55:41 发起的旺顺融 cursor=168 请求成功，下一页 cursor=180 在 11:56:12 记录 REQUEST_TIMEOUT，并自动将全局采集置为暂停。核验时 worker_active=false、request_pending=false，没有自动连续重试。25 秒为定时器目标时限，实际审计约 29 秒，包含调度/数据库写入等待，不能承诺负载下精确 25 秒落库。

同时观测到状态 API 一度超过 15 秒无响应，进程 CPU 使用时间明显增长。故目前保留保护性暂停，不反复恢复请求；下一步须定位本地计算/数据库等待和网络耗时。详见同目录 `2026-09-29-超时保护部署.json`。真实卡顿问题尚未闭环。
